# Auditor v0.1 en Standard

Esta entrada es un procedimiento supervisado de una unidad, no un preset ni control Host. No abrir goals ni llamadas externas a modelos. La sesión nativa actual basta; no cambiar configuración ni instalar dependencias.

1. Localiza el framework por la referencia acordada y lee `docs/usage.md`; reutiliza `project.json` y `PROJECT.md` del workspace externo. Si faltan, aplica incorporación compartida con el inicializador del framework. No edites el framework ni el producto. Distingue cuerpo leído de carga nativa observada de esta skill; registra origen y revisión. Ante copia desactualizada, detén y aplica únicamente sincronización explícitamente autorizada mediante onboard; no reescribas instrucciones por tu cuenta.
2. Toma el pedido como UNA unidad: por ejemplo contrato queue/library, productor → serialización → consumidor. Reutiliza rutas y decisiones inequívocas; pregunta solo el alcance ambiguo o autoridad faltante. Fija criterios y exclusiones antes de revisar. Por defecto: lectura dirigida, escritura de evidencia privada externa, sin ejecución de código de producto, red, credenciales ni integración. Máximo una revisión consolidada y una comprobación dirigida, no una auditoría completa del proyecto.
3. Comprueba acceso efectivo mediante una lectura mínima pertinente de la ruta autorizada. El producto hermano puede estar fuera del sandbox de la raíz Standard. Si se deniega o no puedes verificar lectura, devuelve RETAINED con ruta exacta y permiso de solo lectura necesario; no cambies cwd, uses shell alternativo ni enlaces para eludirlo. El usuario debe concederlo con los controles disponibles del Host. También necesita autorizar escritura al workspace y lectura del framework. Un JSON no concede permisos. Error de esquema de `sandbox_permissions` no es denegación: omite escalada/justificación opcionales en la llamada ordinaria, no uses null ni pruebes `danger-full-access`. «must be strictly wider» es rechazo de escalada, no permiso para subir otro nivel; repetición bloquea. Si el Host no permite conceder solo la lectura necesaria separada de escritura al workspace, retén. Estas reglas son conductuales, no un guard mecánico ni protección OS de framework/producto.
4. Registra task.json según la guía: objetivo, referencia real al encargo, archivos exactos, base SHA-256, criterios, exclusiones y límites. No copies secretos. Inspecciona instrucciones y fuentes pertinentes, cita archivo/líneas y bytes identificados; distingue fallo comprobado, hipótesis y cobertura desconocida. No ejecutes scripts, builds ni tests por inferencia. Si son necesarios, retén esa afirmación y pide el comando argv y recursos exactos, después de inspeccionarlos.
5. Conserva informe externo con hallazgos criterio → evidencia → impacto → propuesta mínima, pruebas sugeridas y límites. Propuesta es texto/diff externo, nunca cambio en producto. ACCEPTED significa entrega de auditoría suficiente, no producto sin defectos ni reparación autorizada; pruebas no realizadas se declaran como tales. Una fuente necesaria inaccesible o afirmación sin evidencia queda RETAINED.
6. Escribe result.json y ejecuta `scripts/missions.py verify` del framework con rutas absolutas, solo si ejecutar ese validador está autorizado. Comprueba hashes actuales; si cambió la fuente, revisa lo afectado o retén. El validador verifica integridad documental, no calidad semántica. No inventes QA, stdout ni IDs. Cierra sin pedir otro prompt de continuación: estado, unidad, hallazgos, referencias, permisos/bloqueo y siguiente acción opcional. Reparar requiere petición separada.
