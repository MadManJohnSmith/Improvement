# Preparación del primer ensayo automatizado del flujo completo

## Decisiones incorporadas

- Enlazar el framework canónico `/home/alan/Documents/Improvement` al workspace de Syncify; no duplicar Improvement dentro del producto.
- Usar DSH **Standard** como modo operativo. El perfil `web` es el servidor/UI de DSH, no el modo Auditoría/Reparación.
- Tratar la instalación de Python real, la carga nativa de skills y la primera auditoría como parte de la prueba, no como prerequisitos artificiales. Los venvs inválidos pueden regenerarse cuando exista CPython real.
- Automatizar mensajes mediante una API soportada de DSH, no mediante teclado, DOM, DevTools ni inyección de UI.

## 1. Preparar el workspace de Syncify

Crear un padre de sesión externo que no esté dentro de un repositorio Git, con una única composición:

```text
<session-root>/
├── framework -> /home/alan/Documents/Improvement
├── product   -> /home/alan/DSH-workspace/projects/Syncify
└── workspace  -> /home/alan/DSH-workspace/workspaces/Syncify
```

El framework sigue siendo una sola copia canónica; `framework` es un enlace de lectura para descubrimiento DSH. El producto es el clon limpio; `workspace` contiene perfil, skills, estado y evidencia. No se copiará framework dentro de Syncify.

Ejecutar `onboard.py` en dry-run y luego `--init` con rutas absolutas para copiar las skills completas al workspace y crear enlaces gestionados bajo `.agents/skills`. Confirmar que el manifiesto externo contiene solo las skills propias y que no hay override `.dsh/skills`.

Preparar una raíz equivalente separada para RehabWeb cuando se vaya a probar ese proyecto; no mezclar dos workspaces en una única raíz gestionada si el script exige un solo workspace por padre.

## 2. Standard DSH

Abrir DSH Standard en el padre de sesión que contiene framework, producto y workspace. El proceso debe conservar ese cwd; no cambiarlo al workspace ni al producto. La copia de skills no demuestra carga.

Comprobar mediante la herramienta nativa `skill`:

1. aparece `workflow-complete-auditor`;
2. origen real apunta al workspace externo;
3. cuerpo coincide con la copia del framework;
4. `workflow-auditor` y `workflow-continuous-repair` también se resuelven;
5. el proyecto se lee y el workspace externo se escribe.

Si la carga nativa falla, dejar `RETAINED` con diagnóstico; no simular la carga leyendo `SKILL.md` manualmente.

## 3. Automatización de mensajes legítima

No automatizar mediante clicks, DOM o teclado. Hay dos vías soportadas:

### A. Typert Remote Session API de DSH

El runtime instalado expone endpoints RPC:

- `session/create`;
- `session/prompt`;
- `session/follow`;
- `session/control`;
- `session/cancel`.

La entrada a `session/prompt` es:

```json
{
  "requestId": "idempotente-y-unico",
  "sessionId": "sesion-standard",
  "mode": "queue",
  "content": [{"type": "text", "text": "..."}],
  "clientTimeZone": "..."
}
```

`queue` es adecuado para enviar el siguiente prompt autorizado; `steer` solo para una corrección urgente. `requestId` evita duplicar mensajes.

El flujo del controlador sería:

1. crear/adoptar sesión Standard con `session/create` y cwd del padre;
2. enviar el prompt de Auditoría completa con `session/prompt`;
3. seguir estado y respuesta con `session/follow`;
4. guardar `sessionId`, `requestId`, estado y recibos externamente;
5. enviar Reparación continua solo después de una autorización/estado válido;
6. cancelar mediante `session/cancel` si el ciclo se detiene.

La API requiere autenticación de la instancia DSH. No se deben imprimir tokens ni asumir que `/api` está disponible sin descubrir el origen/puerto de la instancia.

### B. ACP

ACP es una alternativa para automatizar un proceso hijo por stdio (`initialize`, `newSession`, `prompt`, `cancel`, `close`). Es preferible si se desea un runner reproducible que lance su propia instancia, pero aún requiere componer el servidor ACP y registrar el preset Standard correcto. No se implementará antes de probar el RPC de sesiones existente.

No se usará la API archivada de ZCode ni la inyección de UI: no es el runtime DSH actual ni una interfaz soportada para sesiones Standard.

## 4. Primer prompt automatizado

Una vez validada la skill y la sesión Standard:

> Audita completamente Syncify por unidades funcionales; no modifiques producto ni integres/publices. Divide, revisa, consolida y deja la cola externa para Reparación continua. Usa el workspace externo preparado, conserva el estado del ciclo y detente solo ante decisiones materiales o evidencia faltante.

El Auditor debe terminar con:

- `audit-manifest.json`;
- `audit-report.md`;
- `coverage-matrix.json`;
- `repair-queue.json`;
- `checkpoint.json`;
- `finish.json`.

No se le enviará manualmente “el siguiente ítem”.

## 5. Fases de la prueba

1. preflight y capability;
2. carga nativa de skills;
3. descubrimiento y partición real;
4. subagentes reales o `UNVERIFIED` explícito;
5. consolidación de hallazgos;
6. reparación continua con autorización única;
7. candidatos externos y pruebas reales disponibles;
8. QA independiente o `RETAINED`;
9. reauditoría incremental;
10. archivo compacto y cierre del ciclo.

El primer ciclo no integrará Syncify. La integración requiere autorización separada.

## 6. Python y dependencias

La ausencia de CPython real no bloqueará el inicio de la auditoría estática: forma parte del resultado del preflight. Antes de pruebas Python del producto se intentará preparar un CPython real mediante una ruta/versiones verificadas; no se usarán los venvs ligados al launcher ZCode. npm/Cargo/UI disponibles se mantienen en runtimes externos.

## 7. Intervenciones requeridas

Puedo continuar sin intervención para:

- preparar el enlace/framework y onboarding externo;
- crear los artefactos de sesión;
- inspeccionar el cliente RPC y preparar un runner sin enviar mensajes;
- comprobar carga de skills si Standard está accesible.

Necesito una decisión/permiso solo para:

- enviar el primer prompt automáticamente a una sesión Standard;
- usar la API RPC autenticada de DSH;
- delegar subagentes reales;
- ejecutar reparaciones o pruebas con efectos de producto;
- usar red/credenciales live;
- integrar/publicar.

El envío automático será trazable, idempotente y cancelable; no inyectará texto en la UI.
